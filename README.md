# StadiumIQ — Sports Ticket Demand & Fan Insights

> **🧪 Synthetic portfolio demonstration.** Every record here is generated by `src/generate_data.py`
> with a fixed seed for the fictional **Miami Waves**. The team has no affiliation with any real club or
> league. No real business impact is claimed.

StadiumIQ is a Streamlit analytics app for a ticket operations team. It monitors sales, forecasts the
next seven days of ticket sales, flags games that are behind pace, ranks fans by purchase propensity,
and analyzes a marketing A/B test. The models are evaluated with leakage-safe, chronological methods.

---

## 1. Business problem and intended users

**Users:** ticket operations analysts, the marketing and CRM team, and the revenue manager.

**Questions:**

| Question | Page |
|---|---|
| How are tickets, revenue and sell-through tracking? Is a game ahead of or behind similar games at the same lead time? | Sales Overview |
| How many tickets will each upcoming game sell in the next 7 days? | 7-Day Forecast |
| Which games will miss their 7-day checkpoint target, and which are nearly full? | Recommendations |
| Which eligible fans should get reminder outreach for the game 14 days out? | Fan Propensity |
| Did a personalized ticket email convert better than the standard one? | A/B Experiment |

## 2. Features

- **Sales Overview.** Season and game filters; KPI cards (tickets, revenue, sell-through, remaining
  inventory); daily and cumulative sales; sell-through vs. target by game; a pace curve by days until
  kickoff against comparable completed games at the same lead time; an upcoming-games table with
  forecast status.
- **7-Day Forecast.** A recent-7-day-average baseline and a recursive XGBoost forecast, plus a chart
  with as-of and kickoff markers, a downloadable CSV, and expandable backtest metrics by horizon and game.
- **Fan Propensity.** A live, ranked list of eligible fans for the game 14 days after the as-of date,
  with filters and CSV export. Also includes a Logistic Regression vs. Random Forest comparison,
  a confusion matrix, a calibration check and feature drivers.
- **Recommendations.** Rule-based cards, each with a trigger metric, threshold, explanation and
  suggested action. A chart explains how the checkpoint target is derived.
- **A/B Experiment.** An intention-to-treat analysis: sample sizes, conversion rates, difference in
  percentage points, relative lift, 95% CI, a two-proportion z-test, a sample-ratio-mismatch check,
  power, and a plain-language interpretation.
- **Data & Methods.** Schema row counts, simulation assumptions, the leakage-safeguard table and limitations.

Training happens only in `bootstrap`. The app loads saved artifacts through `st.cache_data` and
`st.cache_resource`, keyed on the database file's modification time, so it never retrains during
interactions.

## 4. Installation and startup

Requires Python 3.11+ (tested on 3.13).

```bash
python -m venv .venv && source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python -m src.bootstrap          # generate data, build SQLite, train + evaluate, save artifacts (~75 s)
streamlit run app.py             # open http://localhost:8501
python -m pytest                 # 42 tests (page smoke tests need bootstrap to have run)
```

`data/`, `models/` and `reports/` are git-ignored and fully reproducible. Re-running the bootstrap
produced byte-identical metrics files.

### Deploying for free

If the artifacts are missing, the app builds them itself on first launch. It shows a "First launch"
spinner for about 2 minutes, after which every page loads instantly. A fresh clone therefore deploys
with no extra steps. The build peaks at about 900 MB of RAM. The pages only read the database and
`reports/`; the model files are not loaded at view time.

**Option A: Streamlit Community Cloud (free, simplest)**
1. Push this folder to a GitHub repository (public, or private with Streamlit's GitHub app).
2. Go to <https://share.streamlit.io>, sign in with GitHub, click **Create app**, and choose the repo,
   branch `main` and main file `app.py`. Under *Advanced settings*, pick Python 3.12.

**Option B: any Docker host (Hugging Face Spaces with the Docker SDK, Render, Fly.io, ...)**

```bash
docker build -t stadiumiq .
docker run -p 8501:8501 stadiumiq          # http://localhost:8501
```
The container listens on `$PORT` (default 8501). On Hugging Face Spaces, set `app_port: 8501` in the
Space's README front matter, or set the `PORT=7860` variable.

## 5. Synthetic data: schema and assumptions

**Simulation as-of date: 2025-10-18** (`src/config.py`). Nothing reads the real clock. Seasons
2020–2024 are complete. In 2025, 4 games are completed and 6 are upcoming, including one 5 days out
(the forecast stops at its kickoff) and one exactly 14 days out (the live propensity snapshot).
Each season has 10 home games at a fictional 5,000-seat venue. There are 5,000 registered fans,
and each game has a 90-day sales window.

| Table | Key fields | Rows |
|---|---|---|
| `games` | game_id, season, opponent, opponent_popularity, game_date, *sales_open_date*, stadium_capacity, base_ticket_price, weekend_indicator, rivalry_indicator, sales_target | 60 |
| `customers` | customer_id, signup_date, preferred_channel, distance_band, fan_segment | 5,000 |
| `transactions` | transaction_id, customer_id → customers, game_id → games, purchase_date, ticket_quantity, price_per_ticket, revenue | 110,035 |
| `engagement` | *engagement_id*, customer_id → customers, engagement_date, channel, engagement_type | 536,064 |
| `experiment_assignments` | experiment_id, customer_id, assignment_date, experiment_end_date, group_name | 4,961 |
| `experiment_outcomes` | experiment_id, customer_id → assignments, purchased, revenue | 4,961 |
| `daily_sales` *(derived in SQL)* | game_id, sales_date, days_until_kickoff, tickets_sold, revenue, is_observed | 5,460 |
| `simulation_metadata` | as-of date, seed, origin | 3 |

The extra fields are justified as follows. `sales_open_date` makes the sales window explicit.
`engagement_id` is a primary key. `daily_sales` is a complete calendar built with a recursive CTE
in which **observed zero-sale days are 0 and not-yet-observed days are NULL**.

**How the simulator works** (these assumptions are why the models find the patterns they find):
- Each fan has an unobserved loyalty level and a yearly interest shock. Loyalty drives both
  engagement frequency and purchase probability.
- The probability that a fan buys for a game rises with opponent popularity, rivalry and weekend games.
  It falls with distance (especially for weeknight games) and with price relative to a reference price.
  Buying the previous home game (habit) raises it, and an unobserved game-level "buzz" shock adds noise.
- Buyers draw a purchase day from segment-specific lead-time profiles (on-sale burst, steady trickle,
  late ramp). Random daily noise and two promotional spikes per game perturb these profiles.
- Purchases are processed chronologically until the venue is full, so sell-outs truncate demand.
- Fans browse more (especially ticket pages) in the three weeks before a purchase.
- Purchases and engagement always occur after signup, and revenue = quantity × price. Current-season
  activity after the as-of date is simulated (so sell-outs stay coherent) but then **discarded**, so
  it never reaches the database.
- The A/B experiment is simulated **independently** of transactions. Its assumed true effect is
  odds × 1.18 (≈ +1.1 pp on a ~7% base rate).

## 6. Models: targets and features

**Forecast.** The target is tickets sold per game per day. Features are days until kickoff, days
since open, day of week, lags at 1, 2 and 7 days, shifted 7- and 28-day rolling means, tickets sold
before the day, remaining inventory (count and share), opponent popularity, rivalry, weekend, and the
base ticket price (fixed before sales open). The model is XGBoost with a `count:poisson` objective,
so predictions are non-negative. Each day is also clipped to the remaining inventory. The baseline
is the game's mean over its last 7 observed days, held flat and capped at inventory.

**Propensity.** The task: *at 14 days before kickoff, predict whether a fan who has not yet bought
tickets for this game will purchase before kickoff.* There is one snapshot per eligible
(fan, game) pair. A fan is eligible if they signed up on or before the snapshot date and had not
bought for this game by then. Games already sold out at the snapshot are excluded. Positive = bought
in (snapshot, kickoff].

Features as of the snapshot date:
- Prior orders, spend, average tickets per order, days since last purchase (plus a never-purchased flag)
- Purchases in the last 365 days, and whether the fan bought the previous home game
- Prior purchases for similar games (same rivalry flag and popularity tier)
- Tenure, engagements and ticket-page views in the preceding 30 days, days since last engagement
- Profile fields, game attributes, and the game's sell-through at the snapshot

Models are a scikit-learn `Pipeline` of Logistic Regression (log1p + standard scaling + one-hot)
and of Random Forest (one-hot). Preprocessing is fit only on training rows.

## 7. Leakage prevention

| Risk | Safeguard (and test) |
|---|---|
| A day's own sales in its features | Lags/rolling means are computed within each game and shifted ≥ 1 day (`test_lags_and_rolling_are_shifted_and_grouped`) |
| Unknown days treated as zero | NULL stays NaN through lags and cumulative sums (`test_unknown_history_is_not_treated_as_zero`) |
| Future actuals in 7-day forecasts | Recursive forecasting: actuals after the origin are dropped, and predictions feed later lags and inventory. Tampering with post-origin actuals leaves forecasts unchanged (`test_forecast_ignores_future_actuals`, `test_recursion_feeds_predictions_back`) |
| Forecasts past kickoff or above capacity | The calendar ends at kickoff; each day is clipped to remaining inventory (`test_forecast_respects_inventory_and_kickoff`) |
| Training on the evaluation period | An expanding-window refit at each origin uses only labels dated ≤ origin (`test_training_rows_respect_cutoff`, `test_rolling_origins_lie_in_evaluation_season`) |
| Future purchases or engagement in fan features | Everything is filtered to dates ≤ the snapshot. Injecting post-snapshot activity leaves features unchanged (`test_features_ignore_future_transactions_and_engagement`) |
| Partially observed outcomes | Only games with kickoff ≤ as-of are used for propensity training and evaluation (`test_only_fully_observed_outcome_windows`) |
| Tuning on the test set | Selection uses 2023; 2024 is scored once afterwards (`test_season_split_is_chronological`) |
| ID memorization | Customer and game IDs are never features (`test_no_ids_or_labels_in_model_features`) |

## 8. Evaluation results (actual output of `python -m src.bootstrap`)

### Seven-day forecast (rolling origins every 7 days; recursive 1–7-day forecasts)

| Season | Approach | MAE (tickets/game-day) | WAPE |
|---|---|---|---|
| 2023 validation (26 origins) | Baseline: recent 7-day avg | 29.15 | 68.3% |
| 2023 validation | XGBoost depth 3 (**selected**) | 12.97 | 30.4% |
| 2023 validation | XGBoost depth 5 | 13.34 | 31.3% |
| **2024 test** (26 origins, 877 points) | Baseline | 31.02 | 74.3% |
| **2024 test** | XGBoost depth 3 | **13.13** | **31.5%** |

Test-season WAPE by horizon (days ahead):

| Horizon | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|
| Baseline | 54.4% | 57.0% | 61.1% | 74.1% | 82.6% | 101.6% | 115.4% |
| XGBoost | 31.0% | 31.0% | 27.1% | 31.3% | 34.0% | 35.3% | 32.9% |

XGBoost beat the baseline on all 10 test games (MAE 10.4–19.7 vs. 21.9–54.6). The flat baseline
cannot anticipate the late-sales ramp or the decay after the on-sale burst, so its error grows with
horizon. The most-used inputs were `lag_1`, `roll_mean_7`, `days_until_kickoff` and `days_since_open`.

### Purchase propensity (chronological season splits)

Splits: train 2020–2022 (30 games, 85,848 snapshots, 25.4% buy), validation 2023 (32,395 snapshots,
21.8%), test 2024 (35,242 snapshots, 19.6%).

| Split | Model | PR-AUC | ROC-AUC | Precision @ top 10% | Lift @ top 10% | Brier |
|---|---|---|---|---|---|---|
| Validation | Logistic (C=0.1) | 0.556 | 0.816 | 64.4% | 2.96× | 0.130 |
| Validation | Logistic (C=1.0) | 0.556 | 0.817 | 64.2% | 2.95× | 0.130 |
| Validation | Random Forest (leaf 20) — **selected** | **0.580** | 0.832 | 65.1% | 2.99× | 0.130 |
| Validation | Random Forest (leaf 80) | 0.573 | 0.828 | 64.8% | 2.97× | 0.131 |
| **Test** | Logistic (C=1.0) | 0.528 | 0.816 | 61.6% | 3.14× | 0.123 |
| **Test** | Random Forest (leaf 20) | **0.561** | **0.834** | **64.2%** | **3.27×** | 0.120 |

The threshold is the per-game top 10% of eligible fans, which is how the outreach list is built.
At that threshold the test confusion matrix is TP 2,267 · FP 1,263 · FN 4,648 · TN 27,064 (recall 32.8%).
The calibration check shows the scores overstate purchase rates in the middle deciles (for example, a
mean score of 0.29 against an observed rate of 0.19), partly because the buy rate fell from season to
season. The app therefore calls them **propensity scores** and uses them for ranking only. The live
list for **Nov 1, 2025 vs Desert Comets** covers 4,047 eligible fans, 405 of them in the top 10%.

### A/B experiment (simulated, intention-to-treat)

| | Control (standard) | Treatment (personalized) |
|---|---|---|
| Assigned | 2,482 | 2,479 |
| Purchasers | 172 | 210 |
| Conversion | 6.93% | 8.47% |

The difference is **+1.54 pp** (relative lift +22.2%), with a 95% CI of **+0.06 to +3.02 pp**.
The two-proportion z-test gives z = 2.04, p = 0.042. The SRM check found no mismatch (χ² = 0.002,
p = 0.97). The test had ~80% power only for effects of about 2.1 pp.

## 9. Business interpretation

- **Forecasting:** a seven-day forecast that tracks the lead-time pattern roughly halves daily error
  compared with a "same as last week" rule in this simulation. That makes weekly pacing reviews more
  reliable than eyeballing recent averages.
- **Pacing:** the Nov 1 game is projected to reach about 2,400 tickets by Oct 25, against the ~2,900
  that comparable completed games had typically sold by that lead time relative to target. It is the
  one game to prioritize in this week's marketing push.
- **Outreach:** the top 10% of eligible fans for Nov 1 bought about 3.3× as often as average in the test
  season. This ranking is useful for reminders and early access. It does **not** show that contacting
  them changes behavior. The right next step is a randomized holdout within the list.
- **Experiment:** the personalized email looks positive, but the interval runs from almost zero to
  3 pp. That is not strong enough to justify the cost of personalization on its own; replicate the
  test or weigh the low end of the interval against that cost.

## 10. Limitations

- Synthetic data does not establish real-world model performance.
- Relationships reflect the generator's assumptions, and the models largely recover what was built in.
- Sales are constrained by inventory. Forecasts and labels describe realized sales, not unconstrained
  demand, and the historical share curve behind checkpoint targets is distorted by sell-outs.
- Purchase propensity is not treatment uplift.
- Using price as a forecasting input does not establish causal price sensitivity. Prices were set with
  knowledge of expected demand, so price is confounded with opponent quality.
- No revenue improvement has been demonstrated.
- Recursive forecasts compound error. Games whose sales open during the forecast week are not forecast.
- Propensity scores are not well calibrated, and the thresholds (7-day checkpoint, 10% "High" shortfall,
  5% near-capacity, top-10% list) are documented business rules, not optimized values.

## 11. Future improvements

- Prediction intervals for the forecast (quantile objectives or conformal residuals) and a
  per-game "probability of hitting target".
- Calibrate propensity scores (isotonic regression on the validation season) so they can be read as probabilities.
- Uplift modeling, using an experiment that randomizes outreach within the high-propensity list.
- Censoring-aware demand estimation for sold-out games.
- Replace the static as-of date with scheduled refreshes, data-quality checks and model monitoring.

## 12. Interview walkthrough (≈ 3 minutes)

1. **Frame it:** "A fictional team's ticket ops team needs to know where sales are heading this week
   and whom to contact. All data is synthetic, with a fixed as-of date of Oct 18, 2025."
2. **Sales Overview:** the Nov 1 game is at 40.7% sell-through, about 2.4 points below the median of 19 comparable completed games at 14 days out.
3. **Forecast:** XGBoost vs. a 7-day-average baseline, evaluated with rolling origins on 2024, which was
   never used for tuning. WAPE was 31% vs. 74%. Explain the recursive forecast, inventory clipping and stopping at kickoff.
4. **Recommendations:** the checkpoint target compares the 7-day projection with where sales *should be in
   7 days*, not with the final target. Nov 1 is flagged.
5. **Propensity:** a precise 14-day snapshot definition, point-in-time features, season splits, and lift
   of 3.3× at the top 10%. Stress that propensity is not uplift and the scores are not calibrated.
6. **Experiment:** ITT, CI of +0.06 to +3.02 pp with p = 0.042, and the SRM check passes. Why I would not
   roll it out on p < 0.05 alone.
7. **Close with limitations:** the results reflect the simulator; the next step is a real holdout test.
